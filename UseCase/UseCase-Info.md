## 1.6.1 UML – уніфікована мова моделювання

*Unified Modeling Language* – уніфікована мова моделювання, що дозволяє моделювати будь-яку предметну область і не тільки для створення програмних продуктів.

Моделювання включає:

- графічні символічні описи;
- структуровані словесні описи.

*UML* для специфікації вимог до програмного продукту містить:

- графічний опис – діаграму варіантів використання (*Use Case*) користувачів програмного продукту;
- словесний опис – сценарії варіантів використання.

**Варіант використання (прецедент)** – це завдання, розв'язуване програмним продуктом (функція програмного продукту), що дозволяє споживачеві-користувачеві отримати якийсь для нього значимий, відчутний і вимірний результат.

### Графічний опис UML-діаграми варіантів використання

Графічний опис *UML*-діаграми варіантів використання програмного продукту (прецедентів) містить:

- актори (символ «людина») як ролі зацікавлених у роботі програмного продукту осіб або зовнішніх щодо програмного продукту інформаційних сервісів;
- прецеденти (символ «овал»), які надають акторам результат, відповідаючи на запитання: «Чого хоче споживач, обравши цей прецедент?»;
- лінії-зв'язку між акторами та прецедентами;
- ієрархічні зв'язки типу «узагальнення» між акторами за наявності спільних для них прецедентів;
- прямокутник як межу використання програмного продукту:
  - всередині розташовані прецеденти;
  - зовні ліворуч/праворуч розташовані актори.

### Опис сценаріїв прецедентів

Опис сценаріїв прецедентів містить наступні елементи:

- назва прецеденту;
- передумови початку виконання сценарію;
- актори як зацікавлені у виконанні сценарію особи;
- актор-основна зацікавлена особа як ініціатор початку сценарію;
- гарантії успіху як гарантований результат, який отримають актори у разі успішного завершення прецеденту;
- основний успішний сценарій виконання прецеденту у вигляді послідовності кроків, наприклад, за шаблоном спілкування між ПП та користувачем:
  1. ПП пропонує користувачу виконати якусь дію.
  2. Користувач виконує дію.
  3. ПП перевіряє результат виконання дії користувача.
- альтернативні сценарії, прив'язані до кроків основного успішного сценарію, які найчастіше пов’язані з обробкою помилок користувача або ПП.

### Рекомендації щодо створення діаграми

1. Визначте ім'я актора як найцікавішої особи у роботі програмного продукту та вкажіть його ім'я поруч із символом «чоловічок».
2. Визначте назву прецеденту, взявши його з опису головних задач, представлених у баченні програмного продукту, або за результатами окремого аналізу довільного тексту-розповіді користувача про свої вимоги.
3. Вкажіть назву прецеденту у символі «овал».
4. Визначте інших акторів, які можуть бути пов'язані із заданим прецедентом.
5. Проаналізуйте можливість об'єднання дій акторів зі створенням узагальнень акторів.
6. Для виявлених узагальнень акторів встановіть зв'язок між ними типу «узагальнення».
7. Визначте інформацію, необхідну для реалізації прецеденту, та визначте акторів і назву прецеденту, за допомогою яких може бути отримана інформація.
8. Визначте можливі зв'язки *include*, у кожному з яких один прецедент є головним прецедентом для вирішення задачі програмного продукту, а другий прецедент є допоміжним, але без якого задачу вирішити буде складно.
9. Визначте можливі зв'язки *extend*, у кожному з яких один прецедент є головним прецедентом для вирішення задачі програмного продукту, а другий прецедент надає альтернативну дію у вирішенні задачі.

Будь-який програмний продукт повинен описуватися діаграмою, що включає два та більше прецедентів 2-х типів:

- прецедент-споживач інформації, що задовольняє споживача;
- прецедент-джерело інформації, що дозволяє в майбутньому задовольнити споживача, виконуючи завдання в іншому прецеденті.

## 1.6.2 Алгоритм визначення акторів

### Джерела для визначення акторів

- **Мета створення ПП** – хто отримує цінність від досягнення мети?
- **Зацікавлені сторони** – хто має інтерес у роботі системи?
- **Контекст використання** – хто взаємодіє із системою в процесі досягнення мети?
- **Зовнішні інформаційні сервіси** – які пристрої або сервіси надають дані чи споживають результати?

### Алгоритм визначення акторів

1. Скласти перелік усіх зацікавлених сторін.
2. Відібрати ті ролі, які безпосередньо взаємодіють із ПП.
3. Класифікувати акторів на:
   - **основних** – ініціюють прецеденти;
   - **допоміжних** – беруть участь у виконанні;
   - **зовнішніх інформаційних сервісів**.
4. Перевірити, щоб кожен актор був асоційований хоча б з одним прецедентом.

### Приклад для ПП інформаційної підтримки тренування з балансувальною дошкою

- **Користувач** – основна зацікавлена особа, яка виконує тренування.
- **Тренер** – допоміжний актор, який супроводжує тренування, налаштовує параметри та формує звіти.
- **Сенсорний блок IMU** – зовнішній пристрій, який передає дані про стан обладнання.

## 1.6.3 Алгоритм визначення прецедентів на основі мети ПП

**Алгоритм містить наступну послідовність кроків.**

1. **Розкласти мету на компоненти.** Мета – це складне твердження, яке містить кілька складових. Їх треба виділити явно.
2. **Для кожного компонента визначити дію та результат.** Кожен компонент описує певну цінність для актора. Цю цінність треба перетворити на дію системи та результат, який отримує актор.
3. **Сформулювати прецеденти.** Прецедент – це завдання, що дає актору значущий, відчутний і вимірний результат. Формулюється як «дієслово + об’єкт»: «Виконати вправу», «Отримати зворотний зв’язок», «Переглянути статистику».
4. **Перевірити повноту та несуперечливість.** Кожен компонент мети має бути покритий хоча б одним прецедентом. Кожен прецедент має простежуватися до компонента мети.

### Приклад опису UML-діаграми мовою PlantUML [7]

```plantuml
@startuml
left to right direction

actor "Користувач" as User
actor "Тренер" as Trainer
actor "Сенсорний блок IMU" as IMU

rectangle "ПП інформаційної підтримки тренування\nз балансувальною дошкою" {

    usecase "Пройти навчальний модуль" as UC_Learn
    usecase "Обрати вправу" as UC_SelectExercise
    usecase "Відкалібрувати сенсор" as UC_Calibrate
    usecase "Зчитати дані з IMU" as UC_ReadIMU
    usecase "Виконати вправу\nз аналізом техніки" as UC_Perform
    usecase "Аналізувати позу,\nрух, симетрію,\nплавність і темп" as UC_Analyze
    usecase "Отримати зворотний зв'язок\nу реальному часі" as UC_Feedback
    usecase "Переглянути статистику" as UC_Stats
    usecase "Отримати рекомендації" as UC_Recommend
    usecase "Сформувати звіт" as UC_Report
    usecase "Налаштувати параметри\nвправ" as UC_Settings
}

User --> UC_Learn
User --> UC_SelectExercise
User --> UC_Perform
User --> UC_Feedback
User --> UC_Stats

Trainer --> UC_Report
Trainer --> UC_Settings
Trainer --> UC_Stats

IMU --> UC_Calibrate
IMU --> UC_ReadIMU

UC_Perform ..> UC_Calibrate : <<include>>
UC_Perform ..> UC_ReadIMU : <<include>>
UC_Perform ..> UC_Analyze : <<include>>
UC_Perform ..> UC_Feedback : <<include>>

UC_Recommend ..> UC_Stats : <<extend>>
UC_Report ..> UC_Stats : <<extend>>

@enduml
